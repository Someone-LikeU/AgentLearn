# 工具系统优化总结报告

## 一、到目前为止已完成的优化

### 1. 工具抽象化
- 新增 `ToolSpec`、`Tool`、`FunctionTool`，将工具从“函数硬编码”升级为“元信息 + 调用接口”的统一模型。
- 工具元信息包含输入/输出 Schema、只读性、并发安全、破坏性、作用域等关键属性。

### 2. 工具注册中心化
- 新增 `ToolRegistry`，将工具查找、导出 OpenAI 格式、函数映射集中管理。
- `ToolManager` 不再直接散落维护工具列表，改为通过注册中心统一输出。

### 3. Agent 解耦
- `Agent` 通过 `ToolManagerConfig` + `AgentToolHandlers` 注入依赖。
- 工具实现、能力判定、MCP 包装从 Agent 内部剥离，Agent 聚焦编排。

### 4. 调度器 V1
- 实现读工具并发、写工具串行的基础批处理调度。
- 保留 `MAKE_PLAN` 特殊流程，确保与既有计划模式行为兼容。

### 5. MCP 能力改造 Step A
- 新增 `mcp_tool_capabilities.json`，显式声明 MCP 工具能力。
- 对未配置 MCP 工具默认保守处理（不可并发读）。
- 当前 `QUERY_WEATHER` 与 `QUERY_FLIGHT_TICKETS` 已配置为可并发只读。

### 6. 调度器 V2
- 调度从“单一只读判定”升级为“运行画像判定”：
  - `is_read_only`
  - `is_concurrency_safe`
  - `side_effect_scope`
- 引入作用域隔离策略：不同作用域不混并发；独占作用域（如 `system`）不并发，进一步降低资源争用风险。

## 二、当前架构带来的收益
- **可维护性提升**：能力分类集中，策略修改点更少。
- **可扩展性提升**：新增工具只需补充 spec 与 handler，调度自动受益。
- **安全性提升**：并发策略从“名称判断”演进到“能力画像判断”。
- **演进成本可控**：本地工具与 MCP 工具在调用层解耦，但在调度判定层逐步统一。

## 三、后续可继续优化方向

### 1. 调度策略增强（V3 候选）
- 增加批次级失败策略：`fail_fast`、`continue_on_error`。
- 增加超时/重试策略，避免单工具阻塞整批任务。

### 2. 能力配置治理
- 为 `mcp_tool_capabilities.json` 增加 schema 校验，启动时提前报错。
- 支持环境级覆盖（dev/test/prod 不同能力策略）。

### 3. 观测与审计
- 输出批次执行日志：批次规划、并发数、耗时、失败率。
- 增加工具调用 trace-id，便于跨模块排障。

### 4. 风险控制
- 对高风险工具（destructive）增加审批策略或策略引擎。
- 增加“作用域互斥组”配置（如文件系统写与某些系统命令互斥）。

### 5. MCP 深化（Step B 以后再评估）
- 当前你希望保持 MCP 与本地工具实现解耦，这一方向合理。
- 后续若需要更强一致性，可仅在“能力画像”层做统一，不强制实现层同构。

## 四、结论
当前工具系统已完成从“函数硬编码”到“能力驱动调度”的关键跃迁。V2 的引入让调度安全性和可控性显著提高，同时保持了与现有 Agent 逻辑的兼容。下一阶段建议优先做“失败策略 + 观测能力”，再决定是否推进 MCP Step B。
